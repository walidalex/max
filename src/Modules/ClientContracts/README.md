# Client contracts

The project/contract directory starts a single Arabic RTL creation wizard at
`/project-contracts/create`. Every wizard submission creates a new project with
its main contract. There is no existing-project or project-only path in the wizard.
The directory uses one expandable project listing without duplicate tabs. Users
with contract view permission only retain a single contract listing.
Project search also matches contract codes, numbers, and titles when the user has
`client_contracts.view`; project-only viewers cannot search hidden contract data.
The existing standalone forms and editing routes remain available.

- The wizard validates each step in the browser and validates the full request
  on the server. Validation failures render the submitted values again.
- Opening and saving the wizard requires both `projects.create` and
  `client_contracts.create`. Each operation is checked again in the service.
  Quick client creation uses the existing endpoint and `clients.create`.
- A new project starts in `planning`; a contract starts in `draft`. The contract
  client is derived from the saved project on the server. Only one main contract
  is allowed per project. Contract numbers are generated by the existing service.
- Cost-plus contracts require a positive markup. Lump-sum contracts require a
  value. BOQ and lump-sum contracts cannot carry markup. BOQ scope is completed
  and approved through the existing contract workflow before activation.
- Project and contract creation share one outer database transaction. Nested
  service transactions use infrastructure savepoints, so inner saves cannot
  commit a partially completed wizard. Quick client creation is a separate save;
  cancelling the wizard does not remove the client.
- Contract states remain `draft`, `active`, `suspended`, `completed`, `cancelled`.
  Existing services enforce transitions and protect commercial fields after
  activation. Future scope steps should reuse those services and invariants.
